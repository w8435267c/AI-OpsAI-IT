# ADR-0003：Task 12 正式文章写入与版本链架构决策

- 状态：Accepted
- 决策日期：2026-10-05
- 适用任务：Task 12 — 文章创建、保存与版本记录
- 决策范围：正式文章写入、KB 编号、草稿保存、版本链、历史恢复、管理侧编辑与预览
- 不代表：Task 12 已开工、相关 Model / Migration / Service / 页面已经实现

## 1. 背景与结论摘要

Task 11 已完成并双端同步。Task 12 当前仍为 `BACKLOG / unassigned`，本 ADR 只冻结后续实施合同，不改变任务状态。

Task 12 V1 采用以下总方案：

1. 正式业务权威继续是 Django 主项目中的 `Article + ArticleVersion`。
2. Task 12 V1 不正式接入 Wagtail，不把隔离 PoC 变成生产入口。
3. KB 编号由服务端在数据库事务内分配，使用单行计数器和行锁保证并发安全。
4. 自动保存原地更新当前草稿；手动保存形成不可变版本节点。
5. 所有更新使用显式乐观锁，冲突时失败并要求用户刷新或另存，不做最后写入者覆盖。
6. 历史恢复复制旧版本内容创建新草稿，不修改旧版本，不回写已发布版本。
7. 员工读取、搜索和详情链保持不变，只读取 `current_published_version`。
8. 编辑入口使用项目自有 Django URL / View / Form / Template / Service。
9. PostgreSQL 并发专项只允许在后续单独授权的隔离临时环境执行；8J 状态不因本 ADR 改变。

## 2. 当前问题

正式模型已经具备文章、版本、工作版本指针和已发布版本指针，但尚缺少一条可安全开放的正式写入链：

- Article 新建入口被安全关闭，因为正式 KB 编号服务尚未实现。
- 尚无统一的创建、自动保存、手动保存、冲突检测和历史恢复 Service。
- 当前 `ArticleVersion` 没有供浏览器提交的乐观锁版本号。
- 当前版本状态无法明确表达“用户已手动保存、但尚未提交审核”的不可变历史节点。
- 正式项目没有员工侧以外的文章管理页面。
- Wagtail 仍是隔离 PoC，不是正式依赖、正式设置或正式路由的一部分。
- SQLite 可以验证一般行为，但不能替代 PostgreSQL 的并发行锁验证。

如果直接开放 ModelForm、Django Admin 新增或 PoC 页面，会绕过 KB 编号、对象级权限、版本不变性和并发控制，因此不可接受。

## 3. 决定采用的方案

### 3.1 正式模型边界

`Article` 负责稳定身份和发布指针，`ArticleVersion` 负责版本化内容。任何页面或 Service 都不得再创建第二套文章正文模型。

`Article.current_published_version` 是员工读取的唯一正式版本指针。

文档中的“当前工作版本 / current working version”是业务语义；在现有模型中的物理字段继续使用 `Article.latest_working_version`。Task 12 V1 不新增同义字段 `current_working_version`，也不为了命名一致性重命名既有字段。

### 3.2 正式写入入口

所有正式写入必须经过 `apps.knowledge` 中的 Service。View、Form、Admin 或测试夹具不得复制业务事务规则。

正式管理页面使用项目自有 Django 路由、视图、表单和模板。Django Admin 继续作为受控维护入口，不承担 Task 12 V1 的普通编辑体验。

### 3.3 版本策略

- 自动保存：更新同一个 `DRAFT` 行，不创建永久历史版本。
- 手动保存：冻结当前 `DRAFT` 为不可变 `SAVED` 节点，并复制为新的当前 `DRAFT`。
- 提交、审核、发布：由 Task 13 负责；Task 12 不新增审核操作。
- 已提交、已审核、已发布、已取代或已保存版本均不可原地改写。
- 历史恢复：把选定历史内容复制为新 `DRAFT`，旧版本保持原样。

## 4. 不采用的方案

### 4.1 不在 Task 12 V1 正式接入 Wagtail

F04A～F08 证明了若干融合方向可行，但它们是隔离实验。正式项目当前没有 Wagtail 根依赖、`INSTALLED_APPS`、正式路由或正式数据迁移。

因此 Task 12 V1：

- 不增加 Wagtail 依赖；
- 不修改正式 settings 以注册 Wagtail；
- 不挂载 Wagtail Admin 或页面路由；
- 不复用 PoC 数据库作为正式数据源；
- 不把 PoC Model、Page 或 Revision 当作正式写入权威。

未来如需 Wagtail 正式接入，必须另立任务，明确数据映射、权限、发布链、回滚和迁移策略。

### 4.2 不使用 `max(kb_no) + 1`

它在并发下会产生重复编号，也会把字符串解析、已删除数据和异常编号带入分配逻辑。

### 4.3 不使用客户端、随机数或时间戳生成 KB 编号

客户端生成可被篡改；随机数不满足顺序与可审计性；时间戳不能可靠解决同一时刻并发，并且暴露实现细节。

### 4.4 不使用进程内锁

多进程、多实例或服务重启后，Python 进程锁不能提供全局唯一保证。

### 4.5 不使用“自动保存即永久版本”

自动保存可能高频触发。每次自动保存都新增版本会制造大量无业务意义的历史节点，并增加存储、查询和审计噪声。

### 4.6 不使用最后写入者覆盖

静默覆盖会丢失另一窗口或另一编辑者的内容，不满足知识内容写入的可追溯要求。

### 4.7 不新增第二套正文结构

Task 12 V1 不新增 RichText、HTML、StreamField 或第二个 JSON 正文字段。未知 HTML 不进入正式员工渲染链。

### 4.8 不做 ArticleVersion + Wagtail Revision 双写

双写会产生正文、状态、权限和失败回滚的双权威问题。Task 12 V1 只写 ArticleVersion，不同步创建或更新 Wagtail Revision。

### 4.9 不追求 gapless KB 编号

事务回滚、删除和保留策略都可能形成空号。系统不为了填补空号重用已成功提交的编号，也不串行化与业务正确性无关的“绝对连续”要求。

### 4.10 不让草稿复用员工正式详情 Reader

草稿预览必须走独立管理权限链。`/kb/<kb_no>/` 和 `get_employee_article_detail` 永远不接受“预览草稿”参数。

### 4.11 不提前实现 Task 13

Task 12 不实现提交审核、批准、驳回、发布、重新发布或审批流，即使现有模型已经存在部分状态字段。

## 5. Article 职责

`Article` 只承担稳定、跨版本的业务身份：

- 全局唯一且不可变的 `kb_no`；
- 所属知识空间、分类、Owner、内容策略和生命周期状态；
- 当前工作版本指针 `latest_working_version`；
- 当前已发布版本指针 `current_published_version`；
- 建立人、时间戳等稳定元数据。

`Article.title` 不作为独立可编辑的第二内容源。Task 12 V1 把它视为服务端维护的兼容投影：

- 创建时由首个草稿标题初始化；
- 后续不得由客户端单独提交；
- Task 13 发布时再决定其与正式发布标题的同步时点；
- 员工首页、分类、详情和搜索继续从 `current_published_version` 读取标题。

## 6. ArticleVersion 职责

`ArticleVersion` 是内容快照权威。Task 12 V1 沿用现有字段体系：

- `version_no`
- `status`
- `title`
- `summary`
- `applicable_scope`
- `body`
- `body_plaintext`
- `change_summary`
- 创建、提交和发布时间字段

现有模型已经明确 `body` 是版本正文权威，`body_plaintext` 是员工展示、搜索、差异比较和后续 RAG 使用的派生投影。Task 12 V1 保持这个单向关系，不把 `body_plaintext` 提升为第二正文权威。

Task 12 V1 的编辑器只呈现纯文本输入。Form 使用独立输入名 `body_text`；Service 不接受客户端分别提交 `body` 与 `body_plaintext`，而是一次性生成：

- 权威 `body`：`{"format": "opsai.plaintext/1", "text": "<纯文本>"}`；
- 派生 `body_plaintext`：与 `text` 完全相同的普通字符串。

该最小 schema 使用现有 JSONField，不增加第二个正文 JSON。`format` 必须严格匹配，字段必须使用白名单，`text` 必须是字符串；未知格式失败关闭，不做“看起来像文本”的猜测。

既有版本的 `body` 和 `body_plaintext` 原样保留。历史复制必须同时复制两者；遇到未知旧 `body` 结构时，V1 可以只读和原样复制，但不得隐式用 `body_plaintext` 反向覆盖权威 `body`。需要编辑未知旧结构时，必须先经过显式、可审计的转换确认；该转换不属于 Task 12 的默认保存路径。

后续若引入 RichText 或更复杂结构化正文，必须另立 schema、迁移和渲染决策。

## 7. 当前工作版本与已发布版本

同一篇 `Article` 在任一时刻：

- 至多有一个当前工作版本；
- 至多有一个当前已发布版本；
- 两个指针可以同时存在并指向不同版本；
- 员工读取只跟随已发布指针；
- 管理侧编辑只操作工作指针所指向的 `DRAFT`。

### 7.1 current_working_version

这是本 ADR 使用的业务语义名称，不是新增字段。现有 `Article.latest_working_version` 已足以承担该指针，Task 12 不重复造字段。

Task 12 的创建、自动保存、手动保存和历史恢复完成后，该指针必须指向当前唯一可编辑的 `DRAFT`。现有模型为 Task 13 预留的 `IN_REVIEW` / `REJECTED` 兼容范围不授权 Task 12 提前实现审核状态转换。

Task 12B 应把 Article 的模型校验收紧为“该指针为空或指向本 Article 的 DRAFT”。实施前若发现既有数据指向 `IN_REVIEW` / `REJECTED`，必须停止并报告，不得静默改写历史。将来 Task 13 提交草稿时，应清空工作草稿指针；驳回后如需继续编辑，应复制为新 DRAFT，具体事务由 Task 13 另行冻结。

### 7.2 current_published_version

现有 `Article.current_published_version` 直接复用，不新增替代字段。Task 12 的任何操作都不得移动、清空或改写该指针；只有 Task 13 的正式发布事务可以改变它。

“Published A + Draft B”时：

- 员工首页、分类、详情和搜索只能看到 A；
- 管理侧编辑页面看到并修改 B；
- B 的标题、摘要、正文和变更说明不得进入员工 Reader 或搜索结果；
- B 未发布前不得改变 A。

## 8. KB 编号合同

正式格式固定为：

`KB-000001`

规则：

1. 全局唯一，不按空间、分类或年份重置。
2. 首次创建 Article 时由服务端分配。
3. 创建成功后永久不可修改，也不允许客户端提交。
4. 允许因为事务失败、删除、导入或保留策略出现空号；空号不是故障。
5. 不承诺连续无空洞，只承诺成功记录唯一、稳定和格式正确。
6. V1 范围为六位数字；耗尽前必须另立扩容决策，不静默改变格式。

## 9. KB 编号并发设计

Task 12B 计划新增最小计数器模型 `KnowledgeNumberCounter`：

- 使用固定主键标识唯一计数器行；
- 保存下一可分配整数 `next_value`；
- 由 Migration 创建结构并初始化；
- 业务代码不得依赖手工预置。

Article 创建 Service 在同一个 `transaction.atomic()` 中：

1. 使用 `select_for_update()` 锁定计数器行；
2. 读取并校验 `next_value`；
3. 生成 `KB-{value:06d}`；
4. 递增计数器；
5. 创建 Article；
6. 创建首个 ArticleVersion 草稿；
7. 设置 `latest_working_version`；
8. 整体提交。

`Article.kb_no` 的数据库唯一约束继续作为最后防线。唯一冲突、计数器缺失、编号耗尽或事务异常都必须失败关闭，不得退回 `max + 1`。

PostgreSQL 的行锁是正式并发语义。SQLite 测试只验证服务行为和回滚，不作为 `select_for_update` 并发结论。

## 10. Article 创建事务

创建请求至少包含经 Form 校验的空间、分类、标题、摘要、纯文本正文、适用范围和变更说明。

服务端负责：

- 验证操作者和对象级权限；
- 验证空间与分类的父子关系及启用状态；
- 强制或校验 Owner；
- 忽略客户端提供的 KB 编号、版本号、状态和指针；
- 在一个事务内分配编号、创建 Article、创建版本 1 草稿并设置工作指针；
- 任一步失败时整体回滚，不留下无版本 Article 或孤立版本。

首个版本规则：

- `version_no = 1`；
- `status = DRAFT`；
- `lock_version = 1`；
- `current_published_version = NULL`；
- `latest_working_version` 指向版本 1。

## 11. 自动保存语义

自动保存只允许修改当前 `latest_working_version` 指向的 `DRAFT`。

请求必须带：

- Article 标识；
- 当前草稿标识；
- 客户端读取时的 `expected_lock_version`；
- 经过 Form 校验的可编辑内容。

成功时：

1. 在事务内锁定 Article 与当前草稿；
2. 再次确认指针、状态、Owner 与对象权限；
3. 比较 `expected_lock_version`；
4. 更新当前草稿内容；
5. `lock_version` 加一；
6. 返回新锁版本号。

自动保存：

- 不改变 `version_no`；
- 不创建新的 ArticleVersion；
- 不修改已发布指针；
- 不修改已发布内容；
- 不吞掉校验错误或冲突；
- 不承诺离线合并。

## 12. 手动保存与版本节点

为表达“已保存但尚未提交审核”的不可变历史，Task 12B 计划在现有版本状态中增加 `SAVED`。

手动保存成功时，在一个事务内：

1. 校验对象权限和 `expected_lock_version`；
2. 把提交内容写入当前 `DRAFT`；
3. 将该行状态改为 `SAVED`，成为不可变历史节点；
4. 使用其完整内容复制创建下一个 `DRAFT`；
5. 新草稿使用新的 `version_no` 和 `lock_version = 1`；
6. 更新 `latest_working_version` 指向新草稿；
7. `current_published_version` 保持不变。

`version_no` 在版本节点创建时分配，创建后不可修改。版本创建 Service 先对 Article 行加锁，再基于该 Article 已存在的最大版本号分配下一值；数据库 `(article, version_no)` 唯一约束作为最后防线。

当前“非草稿必须有 submitted_at / submitted_by”的约束需要在 Task 12B 最小调整，使 `SAVED` 不被当作已提交状态。`SAVED` 不是审核通过或发布状态。

## 13. 乐观锁合同

Task 12B 计划为 `ArticleVersion` 增加 `lock_version` 正整数列，默认值为 1。

所有自动保存、手动保存和历史恢复请求都必须携带 `expected_lock_version`。更新条件不匹配时：

- 不覆盖数据库内容；
- 不自动合并；
- 不隐式重试写入；
- 返回明确冲突响应；
- 页面提示用户刷新后重新应用修改，或把本地文本复制保存到别处。

服务器返回的冲突信息不得包含操作者无权读取的内容。

## 14. 历史版本恢复

历史恢复不是“把旧版本改回草稿”，也不是“移动发布指针”。

恢复操作：

1. 仅允许选择当前 Article 下的不可变历史版本；
2. 校验操作者对 Article 的对象级管理权限；
3. 校验当前草稿的 `expected_lock_version`；
4. 在事务内先把当前草稿安全冻结为 `SAVED`；
5. 复制目标历史版本的内容创建新的 `DRAFT`；
6. 分配新的 `version_no`；
7. 更新 `latest_working_version`；
8. 保持 `current_published_version` 不变。

Task 12B 计划增加可空、自关联、受保护的来源字段，例如 `restored_from_version`，记录新草稿从哪个版本复制。该字段只表达血缘，不允许反向修改来源版本。

恢复后的内容必须重新经历后续 Task 13 的提交、审核和发布，不能因为来源曾经发布过而自动获得发布资格。

## 15. 不可变状态

Task 12 写入 Service 把以下版本视为不可原地修改：

- `SAVED`；
- `IN_REVIEW`；
- `REJECTED`；
- `PUBLISHED`；
- `SUPERSEDED`。

Task 13 可以定义审核拒绝后的继续编辑流程，但必须通过新草稿或显式状态转换完成，不能覆盖已提交、已审核或已发布的历史证据。

任何模型级后门、Admin 表单或脚本都不得绕过这项合同。

## 16. 员工读取与搜索隔离

Task 12 不修改以下正式读取契约：

- `employee_visible_articles`
- `get_employee_article_detail`
- `visible_articles`
- `can_read_article`
- 首页、分类、详情和搜索现有路由

员工侧继续只读取：

- 可见 Article；
- `current_published_version`；
- 当前账号、受众、DENY 优先、生命周期和发布时间规则允许的内容。

以下内容不得进入员工列表、详情、搜索、计数或侧信道：

- DRAFT；
- SAVED；
- IN_REVIEW；
- REJECTED；
- 未成为当前发布版本的历史 PUBLISHED；
- 管理预览内容；
- 无权限 Article 的标题、摘要、正文或存在性。

## 17. 正式管理入口与预览

Task 12E 使用项目自有 Django 管理页面，建议命名空间与员工页面分离，例如：

- `/manage/knowledge/articles/new/`
- `/manage/knowledge/articles/<article_id>/edit/`
- `/manage/knowledge/articles/<article_id>/history/`
- `/manage/knowledge/articles/<article_id>/preview/`

最终路径由 Task 12E 结合现有 URL 结构落地，但必须保持管理侧与员工侧权限链分离。

预览规则：

- 仅 GET；
- 仅通过管理侧对象权限后访问；
- 默认预览当前工作草稿；
- 响应设置 `Cache-Control: private, no-store`；
- 不加入员工搜索索引或可见计数；
- 使用 Django 模板自动转义；
- V1 纯文本正文不得通过 `safe` 直接输出；
- 无权限时统一失败，不泄露标题、摘要、正文、版本号或存在性。

## 18. 权限与对象级授权

Task 12 V1 不把 `is_staff` 或 `is_superuser` 当作正式业务授权。超级用户如果没有项目定义的角色与对象权限，也不得仅凭超级用户身份通过 Task 12 管理页面。

允许角色：

- 知识编辑员；
- 知识管理员。

共同门槛：

- 用户已认证、账号启用且业务账号状态有效；
- 拥有相应 Article / ArticleVersion model permission；
- 属于项目现有知识编辑员或知识管理员角色；
- 满足对象级规则。

对象级最小规则：

- 知识编辑员只能创建在自己负责的知识空间内，创建时 Owner 强制为自己；
- 知识编辑员只能编辑自己拥有的 Article，或其所属空间由自己负责的 Article；
- 知识管理员可以管理有效知识空间内的 Article，并可选择有效 Owner；
- 分类必须属于所选空间且处于有效状态；
- 任何客户端提交的 Owner、空间、分类都由服务器重新校验。

如果后续发现现有字段不足以表达“负责的知识空间”，不得用 staff / superuser 兜底；应提出范围问题或单独增加明确授权模型。

## 19. 与 Task 13 的边界

Task 12 负责：

- Article 创建；
- KB 编号；
- 当前草稿编辑；
- 自动保存；
- 手动保存与不可变历史；
- 乐观锁冲突；
- 历史恢复到新草稿；
- 管理侧编辑与预览。

Task 13 负责：

- 提交审核；
- 审核人选择或分配；
- 审核通过与驳回；
- 发布和重新发布；
- `current_published_version` 的正式切换；
- 已发布版本转为 `SUPERSEDED` 的规则；
- ReviewRecord 与审核审计闭环。

Task 12 不提前实现 Task 13 的按钮、状态转换、通知或发布事务。

## 20. 既有数据与迁移策略

Task 12B 只允许增量迁移，不重写既有文章内容：

- 新增计数器模型；
- 新增 `lock_version`；
- 新增 `restored_from_version`；
- 增加 `SAVED` 枚举并最小调整相关 CheckConstraint；
- 收紧 `latest_working_version` 的模型校验，只允许为空或指向当前 Article 的 `DRAFT`；
- 为既有 ArticleVersion 回填 `lock_version = 1`；
- 不修改既有 `kb_no`；
- 不改变既有 `current_published_version`；
- 不把历史版本批量改为 `SAVED`；
- 不从 PoC 数据库导入正式数据。

Migration 必须可在空库和含既有数据的库上前向执行。回滚设计以代码与 schema 反向迁移为主；任何可能丢失血缘或锁版本的数据降级必须在执行前另行评估。

## 21. PostgreSQL 隔离验证合同

常规开发先在正式测试设置下使用 SQLite 验证：

- 创建事务回滚；
- 编号格式与唯一约束；
- 自动保存；
- 手动保存；
- 冲突响应；
- 历史恢复；
- Published A + Draft B 隔离；
- 对象级权限与预览安全。

在 Task 12 封板前，应另行申请 PostgreSQL 隔离专项授权，验证：

- `select_for_update` 是否真正串行化编号分配；
- 多事务同时创建 Article 时是否无重复编号；
- 自动保存与手动保存竞争时是否正确冲突；
- 版本号并发分配是否保持唯一；
- 死锁或序列化异常是否有限重试并失败关闭；
- 临时数据库、用户、日志和配置是否完整清理。

该专项不得读取真实 `.env` 或 `D:\OpsAI-Handoff\LocalConfig\OpsAI.env`，不得操作持久 PostgreSQL，不改变 8J 的 `BLOCKED / unassigned` 状态。

## 22. 回滚策略

### 22.1 代码回滚

每个子阶段使用独立 Commit。出现问题时使用 `git revert <commit>` 创建反向提交，不使用 `reset --hard` 或强制推送改写共享历史。

### 22.2 数据库回滚

- 12B 在写入正式数据前验证前向与反向 Migration。
- 一旦 `restored_from_version` 或 `lock_version` 已承载正式数据，降级前必须导出并评估。
- 已成功提交并绑定 Article 的 KB 编号不因后续业务回滚而重新分配给另一文章。
- 已形成的不可变版本节点不通过日常 UI 删除或覆盖。

### 22.3 功能回滚

管理路由可以撤下，但员工 Reader 必须继续读取原有发布指针。关闭编辑入口不得影响已发布知识的首页、分类、详情和搜索。

## 23. 已知风险与控制

| 风险 | 控制 |
| --- | --- |
| 并发创建产生重复 KB 编号 | PostgreSQL 行锁、单行计数器、同一事务、数据库唯一约束 |
| 两个浏览器窗口互相覆盖 | `lock_version` 乐观锁，冲突时失败，不做最后写入者覆盖 |
| 自动保存制造版本爆炸 | 自动保存原地更新当前 DRAFT |
| 手动保存没有可审计节点 | 冻结为不可变 SAVED，再创建新 DRAFT |
| 历史恢复篡改证据 | 复制为新草稿并记录 `restored_from_version` |
| 草稿泄露给员工 | 员工链只跟随 `current_published_version` |
| 管理预览被缓存或索引 | 管理权限、GET、`private, no-store`、不进入 Reader |
| Superuser 绕过业务授权 | 显式角色、model permission、对象级规则，不以 superuser 兜底 |
| JSON 正文和纯文本正文双权威 | Form 只收 `body_text`；Service 写入权威 `body` 并同步生成派生 `body_plaintext` |
| PoC 被误当正式能力 | Task 12 V1 不接入 Wagtail，未来另立正式融合任务 |

## 24. 从 F04A / F04B / F07 / F08 继承的经验

### F04A

- Article 只能有一条正式内容权威链。
- 草稿与正式发布内容必须隔离。
- 版本追加、权限检查和事务回滚是融合前提。
- PoC 证明方向，不自动成为正式实现。

### F04B

- 草稿保存必须经过明确的路由、动作和权限闭环。
- 高频自动保存与“每次保存都追加永久 revision”存在冲突。
- 因此正式 V1 区分自动保存和手动保存，不照搬 PoC 的 autosave 关闭或 revision 行为。

### F07

- 数据迁移必须记录来源、幂等、原子并保持旧记录不变。
- 数据库自增空洞不等于事务失败；KB 编号同样允许空号。
- PoC 数据不直接导入正式表。

### F08

- 正文转换不能把未知 HTML 当作可信内容。
- 草稿和发布内容必须保持隔离。
- V1 使用纯文本展示与自动转义，不引入未经设计的 RichText / StreamField。

## 26. 验收准则

后续 Task 12 只有在以下事实均有证据时才能进入 VERIFY：

1. 两个并发创建请求不会成功写入重复 KB 编号。
2. 创建中任一步失败不会留下 Article、版本或计数器半成品。
3. 自动保存不增加永久版本节点。
4. 手动保存形成不可变 SAVED 节点和新的当前 DRAFT。
5. 旧锁版本写入会明确冲突，不覆盖新内容。
6. 历史恢复创建新版本并保留来源血缘。
7. Published A + Draft B 时员工首页、分类、详情和搜索只看到 A。
8. 无对象权限者看不到管理内容、预览内容或对象存在性。
9. staff / superuser 身份本身不能绕过业务角色和对象规则。
10. 员工 Reader、搜索和权限回归保持通过。
11. Model / Migration 变更仅限本 ADR 冻结的最小集合。
12. PostgreSQL 并发结论来自隔离专项，不由 SQLite 推断。
