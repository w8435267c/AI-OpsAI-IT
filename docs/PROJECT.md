# OpsAI 项目说明

本文档是 OpsAI 的长期项目说明，用来回答“这个项目是什么、为什么存在、采用什么技术路线，以及 Django 与 Wagtail 当前是什么关系”。它不是项目日报、任务清单、测试报告或 Git 状态记录；会频繁变化的进度应由后续状态与交接文件维护。

## 2. 项目背景

企业内部常见 IT 故障经常被重复咨询，IT 人员需要反复回答相同问题；已有知识又可能分散在个人经验、聊天记录、临时文档和不同工具中，员工难以找到统一、可信且适合当前场景的答案。

未经统一模板、版本和审核管理的操作说明容易过期，也可能出现口径不一致或操作风险。与此同时，独立网站会增加记网址和重新登录的门槛；在电脑不可用时，员工还需要能通过手机查看排障步骤。部分 IT 内部 SOP 或运维案例也不能对所有员工公开。

OpsAI 因此希望把经过审核的 IT 经验沉淀为可搜索、可分类、可追踪版本并受访问控制的知识。员工从日常使用的钉钉工作台进入并优先自助解决问题；知识无法解决时，再跳转到公司现有的统一 IT 服务入口，形成“先知识、后服务”的闭环。

## 3. 目标用户

- 普通员工：搜索、浏览本人有权访问的知识，并在知识无法解决问题时进入现有 IT 服务入口。
- 知识编辑员：创建和维护知识草稿，提交审核。
- 知识审核员：检查内容的准确性、安全性、适用范围和表达质量，处理审核与复审。
- 知识库管理员：维护知识空间、分类、内容授权和知识运营配置。
- IT 运维人员：既是知识的重要提供者，也是内部 SOP、运维案例和故障经验的使用者。
- 系统集成管理员：维护钉钉应用配置、身份同步、通知和集成故障；该角色不自动拥有内容审批权。

## 4. 项目核心目标

1. 将分散的 IT 故障处理经验沉淀为有负责人、有版本、有审核记录且可以持续复审的知识。
2. 让员工通过关键词、分类和标签找到经过审核、当前有效且本人有权阅读的内容。
3. 在服务端同时落实账号状态、系统操作权限和内容受众权限，敏感知识不能只依赖前端隐藏。
4. 建立草稿、提交、审核、发布、复审、下架和归档的内容生命周期，并保留必要的历史与审计证据。
5. 以钉钉工作台作为统一入口，逐步实现免登身份、用户映射、必要通知和移动端使用体验。
6. 当知识无法解决问题时，安全地跳转到现有统一 IT 服务入口；本期不另建完整 ITSM。
7. 为以后基于已审核知识的 AI 问答和更深入的 ITSM 联动保留清晰边界，但不在 V1.1A 提前实现这些后续能力。

## 5. 当前项目范围

本节描述 V1.1A 的产品建设边界，不代表其中每项能力都已经实现或上线。实际成熟度见第 10、11 节。

- 员工侧知识浏览、分类导航、全文检索、筛选、零结果处理和知识详情阅读。
- 文章、版本、受众、审核、发布、复审、下架和归档等知识生命周期。
- 系统操作角色与内容受众分离，搜索、详情和附件均在服务端先做受众过滤。
- 钉钉企业内部 H5 入口、免登身份、用户映射、必要通知和 PC / 手机响应式访问。
- 私有附件、访问鉴权、病毒扫描和访问审计。
- 知识未解决时跳转到现有统一 IT 服务入口，并保留最小且安全的上下文。
- 支撑上述能力的审计、幂等、事务、Outbox 和基础运营指标。

## 6. 当前明确不做 / 当前阶段不覆盖

本节只记录当前 PRD 和项目规则已明确排除或延后的范围：

- V1.1A 不建设生成式 AI 问答；基于已审核知识的检索增强问答属于后续 V2.0 方向。
- 不建设完整 ITSM 工单生命周期，只连接现有统一 IT 服务入口。
- 不建设资产全生命周期、账号权限自动治理、软件下载中心或外部门户。
- 收藏、浏览记录、评论、视频、相关推荐、版本差异、批量维护和完整运营看板原则上后置到 V1.1B 或以后。
- 当前架构不引入微服务、React / Vue 前后端分离、Redis、Celery、Elasticsearch、Kubernetes 或独立 API 网关。
- 不为了架构清单而预先批量创建空接口，只实现当前明确授权的任务。

## 8. Django 与 Wagtail 的关系

### 8.1 Django 的定位

OpsAI 最初并且现在仍以 Django 为主体。正式 `config/settings` 注册的是 Django 内置组件和 OpsAI 的 8 个业务 / 集成 App；正式根路由当前没有挂载 Wagtail。`accounts.User`、组织关系、系统角色、知识稳定身份、内容受众和各 App 的业务职责继续由 OpsAI 管理。

Django 不是准备被删除的旧框架。Wagtail 本身也构建在 Django 之上，因此当前方向是在现有 Django 项目中按边界复用 Wagtail，而不是用另一个独立系统整体替换 OpsAI。

### 8.2 为什么引入 Wagtail

OpsAI 需要可靠的内容编辑、修订历史、草稿与正式版本隔离、审核工作流和发布基础能力。完全自行维护这些通用 CMS 能力成本较高，Wagtail 已提供可扩展的 Revision、DraftState、Workflow 和 Snippet 管理机制，因此项目选择验证复用这些基础能力。

引入 Wagtail 不改变 OpsAI 的业务安全要求。内容受众的拒绝优先、作者不得自审、批准修订与实际发布修订必须一致、历史证据保留以及业务状态、审计和 Outbox 的事务一致性，仍需由 OpsAI 的服务端适配层保证，不能直接假定 Wagtail 默认行为已经满足。

### 8.3 当前实际关系和融合程度

目标架构已经明确为“OpsAI Django 主项目 + Wagtail 内容管理基础能力”，但当前实现成熟度仍是**隔离 PoC，而非正式切换**：

- `pyproject.toml` 的正式运行依赖尚未包含 Wagtail，正式 `INSTALLED_APPS` 和 `config/urls.py` 也没有注册 Wagtail。
- Wagtail 相关模型、设置、后台路由、审核发布服务、迁移演练和员工详情页均位于 `experiments/wagtail_f02`～`wagtail_f08`。
- 隔离实验已经验证版本兼容、后台准入、候选一对一 `KnowledgeContent` Snippet、追加修订、审核与批准、禁止自审、正式修订快照读取、拒绝优先的受众校验、旧内容导入演练、普通文本转换、空正文审核拦截以及最小员工详情页。
- 上述结果证明融合路线具备继续推进的技术基础，但实验使用合成配置和 SQLite 内存库；部分页面只存在于实验 URL，不能描述为正式员工入口或生产上线。
- 正式内容模型、生产迁移、正式路由切换、PostgreSQL、并发、批量数据、部署与回退仍需后续设计和验证。旧 `ArticleVersion`、`ReviewRecord` 及业务指针在切换完成前不得删除或伪造替代。

因此，当前关系应理解为：**融合方向已确认，核心链路已形成隔离验证证据，正式业务接入尚未完成**。不应理解为“Wagtail 已整体替换 Django”，也不应把 F02～F08 的实验代码视为完整生产功能。

## 10. 能力成熟度说明

项目使用以下四类状态，避免把“存在代码或测试”误写为“已正式上线”：

| 状态 | 定义 | 当前典型能力 |
| --- | --- | --- |
| 正式接入 | 已进入当前项目正式配置或业务调用路径，不只存在于实验目录 | Django 工程骨架、健康检查、正式账号与知识核心模型、Django Admin 保护、本地开发角色与模拟登录、开发用 PostgreSQL Compose 环境 |
| PoC / 隔离实验 | 为验证方案而存在，能够提供技术证据，但不能直接描述为生产功能 | Wagtail F02～F08 的兼容、内容修订、后台编辑、审核发布、员工读取、旧内容迁移和实验详情页 |
| 已有测试但尚无完整正式入口 | 底层代码或服务已经验证，但最终用户尚不能通过完整正式路径使用 | `knowledge` 内容受众 Selector；尚未接入正式搜索、知识详情、附件或 HTTP API |
| 规划中 | PRD 或架构已经提出，但当前代码证据不足或尚未正式实现 | 钉钉免登与同步、正式搜索、完整发布事务、附件扫描、服务入口闭环、审计 / Outbox、运营指标及生产化 Wagtail 切换 |

某项能力可能同时具有“实验测试充分”和“尚未正式接入”两个事实；最终归类以实际调用路径为准。详细且会变化的功能进度应记录在后续 `docs/PROJECT_STATE.md`，不在本文件维护完整验收清单。

## 11. 当前开发阶段

项目仍处于 OpsAI 与 Wagtail 的融合开发阶段。现有 Django 主项目已经建立账号、知识核心数据模型、权限基础、健康检查和本地开发环境；Wagtail 方向已经从依赖兼容推进到内容修订、受控审核发布、员工读取、迁移演练和最小页面展示的隔离验证。

这些实验形成了可继续推进的稳定技术证据，但没有改变正式项目配置、正式业务 URL 和生产数据库边界。当前不能声称 Wagtail 融合全部完成，也不能声称知识搜索、钉钉免登、附件、服务跳转或完整内容生命周期已经生产上线。

根 `README.md` 中部分“当前状态 / 下一步”文字仍保留较早阶段描述；理解当前融合进展时，应以实际代码、验证结果、Git 历史及 `docs/PROJECT_STATE.md` 为准。该差异属于动态状态文档滞后，不改变 V1.1A 产品基线和长期安全规则。

## 12. 开发和运行方式概览

- 主要开发环境是 Windows，项目虚拟环境固定在工作区根目录 `.venv`，不全局安装项目依赖。
- 正式工程通过 Django 分环境设置运行；本地开发数据库使用 Docker Compose 提供的 PostgreSQL，Django 可在容器或宿主机虚拟环境中运行。
- 自动测试继续使用 SQLite 内存库；测试结果必须与 PostgreSQL、持久库、并发和生产部署验证明确区分。
- Wagtail PoC 使用隔离 settings、环境白名单和合成数据，不读取真实 `.env`，不复用正式开发数据卷。
- 详细启动、迁移和测试命令以 `README.md`、各实验 README 及当前任务说明为准；执行前应先核验实际分支、依赖和工作区状态。

## 13. 安全与开发基本原则

- 当前开发以 V1.1A PRD 为产品基线；未经授权不得修改 PRD、静默改变产品语义或扩大版本范围。
- 密钥、口令、Token、钉钉凭证和数据库密码只能通过环境变量或受控密钥系统提供，不得写入代码、日志或 Git；`.env` 不得提交。
- 员工读取遵循服务端“拒绝优先”。`is_staff`、`is_superuser`、编辑 / 审核角色、作者或空间负责人身份都不自动绕过内容受众。
- 搜索、详情和附件在返回标题、摘要、正文或文件名之前必须先完成授权；无权访问时不得泄露内容是否存在。
- 发布、审核、下架等核心流程必须通过受控 Service 和数据库事务实现，并覆盖审计、幂等、状态冲突和异常回滚；不能只隐藏页面按钮。
- 正式业务数据不硬删除。文章通过下架或归档退出使用，版本、审核和审计证据按项目规则保留。
- 修改后按影响范围运行检查和测试；SQLite 实验、静态检查或测试通过不能替代 PostgreSQL、并发、部署或生产验证。
- 不擅自读取或修改真实业务数据，不执行破坏性 Git 操作，不覆盖用户已有改动；提交和推送必须获得明确授权并只包含任务范围内文件。
